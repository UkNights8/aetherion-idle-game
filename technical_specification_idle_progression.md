# ТЕХНИЧЕСКОЕ ЗАДАНИЕ
## Система прогрессии, баланса и механики престижа (Soft Reset) для инкрементальной / Idle-игры

---

### 1. ОБЩИЕ СВЕДЕНИЯ И ТЕРМИНОЛОГИЯ

#### 1.1 Назначение документа
Настоящий документ содержит исчерпывающее техническое описание математических моделей, игровых механик, алгоритмов и технических требований для разработки ядра (Core Loop) инкрементальной игры. Документ предназначен для программистов, геймдизайнеров и специалистов по обеспечению качества (QA).

#### 1.2 Терминология и сокращения
*   **Игровая валюта (Soft Currency)** — базовый накапливаемый ресурс игры (например, золото, монеты, очки).
*   **Престижная валюта (Hard/Prestige Currency)** — мета-ресурс, выдаваемый игроку при перезапуске игры (например, Осколки души, Ангелы).
*   **Мягкий сброс (Soft Reset / Prestige)** — сброс текущего прогресса игрока (зданий, локальной валюты) в обмен на престижную валюту, дающую глобальный перманентный бонус к скорости прогресса.
*   **Здание (Generator / Производитель)** — объект игрового мира, который пассивно генерирует игровую валюту в секунду.
*   **Улучшение (Upgrade)** — модификатор, увеличивающий доходность зданий или кликов.
*   **Временная стена (Time Wall)** — геймплейная точка, в которой время ожидания следующего значимого улучшения становится субъективно неприемлемым для игрока без проведения сброса прогресса (Soft Reset) или совершения внутриигровых покупок.
*   **Milestone Multipliers (Ступенчатые множители)** — резкие скачки эффективности генераторов при достижении определенных уровней владения (25, 50, 100, 250 и т.д.).

### 2. МАТЕМАТИЧЕСКАЯ МОДЕЛЬ ПРОГРЕССИИ

Ядро инкрементальной игры базируется на противодействии экспоненциального удорожания сущностей и линейно-ступенчатого роста генерации ресурсов.

#### 2.1 Формула экспоненциального удорожания зданий
Стоимость покупки каждого последующего уровня здания рассчитывается по формуле геометрической прогрессии:

$$Price(n) = BaseCost \times Multiplier^{n}$$

Где:
*   $Price(n)$ — стоимость покупки следующего ($n$-го) уровня здания.
*   $BaseCost$ — базовая стоимость 1-го уровня здания (задается в таблице баланса для каждого типа здания отдельно).
*   $Multiplier$ — коэффициент роста цены. Стандартный рабочий диапазон: $Multiplier \in [1.07, 1.15]$. Для основных зданий рекомендуется использовать значение $1.15$.
*   $n$ — текущее количество уровней здания, которым уже владеет игрок (начиная с $0$).

#### 2.2 Формула пассивной доходности (Production)
Суммарный пассивный доход в секунду (Idle Income или CPS — Coins Per Second) от всех зданий рассчитывается как сумма доходностей каждого типа здания:

$$Production_{total} = \sum_{i=1}^{M} \left( BaseProduction_i \times n_i \times Mult_{global} \times Mult_{milestone\_i} \times Mult_{upgrades\_i} \right)$$

Где:
*   $BaseProduction_i$ — базовое производство одного здания $i$-го типа за один тик (секунду) без улучшений.
*   $n_i$ — текущее количество зданий $i$-го типа.
*   $Mult_{global}$ — глобальный множитель, зависящий от механики престижа и премиум-эффектов.
*   $Mult_{milestone\_i}$ — ступенчатый множитель здания $i$-го типа.
*   $Mult_{upgrades\_i}$ — локальный множитель улучшений, купленных специально для здания $i$-го типа.

#### 2.3 Ступенчатые множители (Milestone Multipliers)
Для поддержания динамики игры и создания микро-целей для игрока, здания при достижении круглых уровней получают скачкообразное увеличение доходности ($Mult_{milestone}$):

*   При достижении уровня **25**: $Mult_{milestone\_i} = 2$
*   При достижении уровня **50**: $Mult_{milestone\_i} = 4$
*   При достижении уровня **100**: $Mult_{milestone\_i} = 8$
*   При достижении каждых последующих **100** уровней (200, 300, 400 и т.д.): доходность здания умножается на **4**.
*   При достижении уровня **1000**: доходность здания умножается на **10**.

*Примечание: Множители не суммируются, а заменяют друг друга на основе максимального достигнутого порога, либо перемножаются как дискретные события по факту достижения вехи.*

### 3. АЛГОРИТМЫ ОПТОВЫХ ЗАКУПОК (BULK BUY & MAX)

Игрок должен иметь возможность приобретать здания пакетами по **10**, **100** уровней или на всю доступную сумму (**MAX**). Прямой перебор в цикле нагружает процессор и недопустим при работе с большими числами. Вычисления должны производиться аналитическим путем.

#### 3.1 Формула стоимости пакета из $k$ уровней
Для покупки $k$ уровней здания при текущем уровне владения $n$, стоимость ($Cost$) рассчитывается по формуле суммы геометрической прогрессии:

$$Cost(n, k) = BaseCost \times \frac{Multiplier^{n} \times (Multiplier^k - 1)}{Multiplier - 1}$$

#### 3.2 Формула вычисления максимального количества уровней для покупки (MAX)
При наличии у игрока баланса игровой валюты $c$, максимальное количество уровней здания ($k_{max}$), которое он может приобрести «в один клик», рассчитывается по формуле:

$$k_{max} = \left\lfloor \log_{Multiplier} \left( \frac{c \times (Multiplier - 1)}{BaseCost \times Multiplier^{n}} + 1 \right) \right\rfloor$$

#### 3.3 Алгоритм обработки покупок (Псевдокод)
```typescript
function calculateBulkBuy(building: Building, playerBalance: BigDouble, mode: '1' | '10' | '100' | 'MAX'): BulkBuyResult {
    const n = building.currentLevel;
    const b = building.baseCost;
    const m = building.multiplier;

    let k = 1;
    if (mode === '10') k = 10;
    if (mode === '100') k = 100;
    
    if (mode === 'MAX') {
        // Защита от деления на ноль и отрицательного баланса
        if (playerBalance.lessThanOrEqualTo(0)) {
            return { levelsToBuy: 0, totalCost: new BigDouble(0) };
        }
        
        // Вычисление k_max по формуле (3.2)
        const innerTerm = playerBalance.multiply(m - 1).divide(b.multiply(Math.pow(m, n))).add(1);
        if (innerTerm.lessThanOrEqualTo(0)) {
            return { levelsToBuy: 0, totalCost: new BigDouble(0) };
        }
        
        k = Math.floor(Math.log(innerTerm.toNumber()) / Math.log(m));
        if (k < 0) k = 0;
    }

    const totalCost = b.multiply(Math.pow(m, n)).multiply(Math.pow(m, k) - 1).divide(m - 1);

    // Если в режимах "10" или "100" не хватает средств
    if (mode !== 'MAX' && playerBalance.lessThan(totalCost)) {
        // Возвращаем k_max для этой суммы, чтобы кнопка могла стать неактивной 
        // или произвести покупку на максимально возможную сумму в пределах лимита
        return calculateBulkBuy(building, playerBalance, 'MAX');
    }

    return {
        levelsToBuy: k,
        totalCost: totalCost
    };
}
```

### 4. МЕХАНИКА ПРЕСТИЖА (SOFT RESET)

Престиж — ключевой инструмент балансировки игры и удержания пользователей, позволяющий сбросить текущий прогресс в обмен на мета-валюту.

#### 4.1 Формула начисления престижной валюты
Престижная валюта ($P_{earned}$) рассчитывается на основе **кумулятивно заработанной игровой валюты за все время текущего раунда** ($E_{total}$):

$$P_{earned} = \max\left(0, \left\lfloor a \times \sqrt{\frac{E_{total}}{b}} \right\rfloor - P_{current\_spent\_and\_held}\right)$$

Где:
*   $a$ — масштабирующий коэффициент престижа (базовое значение = $150.0$).
*   $b$ — порог первой разблокировки престижа (базовое значение = $1.0 \times 10^{15}$). Престиж становится доступным только при $E_{total} \ge b$.
*   $P_{current\_spent\_and\_held}$ — суммарное количество престижной валюты, уже имеющееся на балансе игрока и потраченное им в древе мета-улучшений за все предыдущие раунды. Предотвращает повторное начисление валюты за уже пройденные этапы.

#### 4.2 Формула глобального баффа от престижной валюты
Каждая единица удержанной на балансе престижной валюты дает аддитивный перманентный бонус к глобальному производству:

$$Mult_{global} = 1 + (P_{held} \times BonusPerUnit)$$

Где:
*   $P_{held}$ — баланс престижной валюты на руках у игрока.
*   $BonusPerUnit$ — базовый бонус одной единицы (по умолчанию = $0.02$, что эквивалентно $+2\%$ к доходу).

#### 4.3 Матрица сброса игрового состояния (Reset Matrix)

При инициации Престижа игровые сущности делятся на две категории:

| Сущность | Статус при сбросе | Комментарий / Обработка |
| :--- | :---: | :--- |
| **Базовая игровая валюта** | **СБРОС** | Баланс устанавливается в стартовое значение (например, 10 монет) |
| **Количество зданий (все типы)** | **СБРОС** | Все уровни зданий обнуляются (уровень = 0) |
| **Локальные апгрейды за обычную валюту**| **СБРОС** | Все купленные улучшения зданий деактивируются и становятся доступными для повторной покупки |
| **Престижная валюта (баланс)** | **СОХРАНЯЕТСЯ** | Начисляется расчетная величина $P_{earned}$ |
| **Постоянные мета-апгрейды (Gacha/Менеджеры)** | **СОХРАНЯЕТСЯ** | Менеджеры, герои и апгрейды древа престижа не сбрасываются |
| **Достижения (Achievements)** | **СОХРАНЯЕТСЯ** | Все открытые ачивки остаются активными, сохраняя свои постоянные бонусы |
| **Игровая статистика (Stats)** | **СОХРАНЯЕТСЯ** | Счётчики общего времени в игре, количества престижей и т.д. |

### 5. СИСТЕМА ОФФЛАЙН-ПРОГРЕССА (OFFLINE PROGRESS)

Для возвращения игрока в игру используется механика накопления ресурсов во время оффлайна.

#### 5.1 Алгоритм инициализации оффлайна
1. При выходе из игры или сворачивании приложения (события `OnApplicationPause` / `OnApplicationQuit`):
   * Записать текущую метку времени в секундах (Unix Timestamp) в локальное зашифрованное хранилище: `last_offline_timestamp = Date.now()`.
   * Сохранить текущее состояние игры.
2. При запуске игры или разворачивании приложения:
   * Проверить метку времени: `current_timestamp = Date.now()`.
   * Вычислить общую продолжительность отсутствия: $\Delta t = current\_timestamp - last\_offline\_timestamp$.
   * Если $\Delta t < 10$ секунд — оффлайн-режим не активируется.

#### 5.2 Формула расчета оффлайн-дохода
Оффлайн-доход не должен рассчитываться через симуляцию игровых тиков секунда за секундой (что приведет к зависанию клиента). Применяется прямая математическая модель:

$$OfflineEarnings = \min(\Delta t, TimeLimit_{offline}) \times Production_{total} \times Efficiency_{offline}$$

Где:
*   $TimeLimit_{offline}$ — максимальное время оффлайн-накопления. Базовое значение = $7200$ секунд (2 часа). Данный лимит может быть увеличен через мета-улучшения или премиум-подписку.
*   $Production_{total}$ — суммарный пассивный доход в секунду на момент выхода игрока из сети.
*   $Efficiency_{offline}$ — эффективность оффлайн-генерации. Базовое значение = $0.5$ (игрок получает только $50\%$ от пассивного дохода). Эффективность может быть улучшена до $1.0$ ($100\%$) через прокачку мета-улучшений или просмотр рекламы (Rewarded Video) при входе.

### 6. ТЕХНИЧЕСКИЕ ТРЕБОВАНИЯ И СИСТЕМНАЯ АРХИТЕКТУРА

#### 6.1 Проблема больших чисел (Big Numbers Support)
Стандартные переменные типа `float` и `double` в большинстве языков программирования следуют стандарту **IEEE 754** и имеют ограничение точности и максимального значения до $\approx 1.79 \times 10^{308}$. В инкрементальных играх баланс легко превышает этот лимит.

*   **Требование**: Использовать специализированный тип данных для хранения баланса и стоимости зданий.
*   **Решение**: Интегрировать библиотеки типа `break_infinity.js` / `break_infinity.cs` или аналогичный самописный класс экспоненциального хранения чисел: `struct BigNumber { double mantissa; int exponent; }`.
*   При вычислениях все переменные доходов и цен должны приводиться к типу `BigNumber`.

#### 6.2 Форматирование отображения чисел для UI
Для предотвращения перегрузки интерфейса гигантскими строками цифр (например, $154,235,162,234,124,124$), игра должна поддерживать три формата отображения (настраивается игроком в меню):

1.  **Дробно-буквенный формат (Standard Notation)**:
    *   До $1,000,000$ — число отображается целиком без округления (например, $985,150$).
    *   От $1,000,000$ до $10^9$ — используется суффикс **M** (Mil) с двумя знаками после запятой (например, $12.54$ M).
    *   От $10^9$ до $10^{12}$ — используется суффикс **B** (Bil) (например, $4.01$ B).
    *   Далее по классической латинской шкале: **T** (Trillion), **Qa** (Quadrillion), **Qi** (Quintillion), **Sx** (Sextillion), **Sp** (Septillion), **O** (Octillion), **N** (Nonillion), **D** (Decillion).
2.  **Научный формат (Scientific Notation)**:
    *   Число отображается в виде мантиссы от $1.00$ до $9.99$ и степени экспоненты (например, $1.54e15$, $8.90e302$).
3.  **Инженерный формат (Engineering Notation)**:
    *   Степень экспоненты всегда кратна 3, а мантисса находится в диапазоне от $1.00$ до $999.99$ (например, $154.20e12$, $1.54e15$).

#### 6.3 Безопасность и защита от читерства
Поскольку оффлайн-прогресс завязан на времени устройства, игра уязвима для читерства методом перевода системных часов вперед.

*   **Локальная валидация**:
    *   Запретить начисление оффлайн-прогресса, если $\Delta t$ имеет отрицательное значение (игрок перевел время назад).
    *   Сравнивать время девайса с показаниями высокоточного внутреннего таймера устройства (например, `Time.realtimeSinceStartup` в Unity), чтобы предотвратить накрутку внутри одной игровой сессии.
*   **Серверная валидация (Рекомендуется)**:
    *   Запрашивать точное время с доверенного NTP-сервера при запуске игры. Сравнивать разницу во времени с момента последнего сохранения именно по серверному времени.
    *   При отсутствии интернета временно блокировать начисление оффлайн-дохода свыше стандартного 2-часового лимита во избежание масштабного абьюза.

### 7. КРИТЕРИИ ПРИЕМКИ (ACCEPTANCE CRITERIA)

1.  **Точность формулы стоимости**: Покупка 10 и 100 зданий «в один клик» через аналитический алгоритм должна стоить ровно столько же, сколько стоила бы поочередная покупка этих уровней по одному. Погрешность из-за округления типов данных с плавающей точкой не должна превышать $0.0001\%$.
2.  **Работоспособность престижа**: После сброса игрок получает точно рассчитанный объем валюты престижа, глобальный модификатор дохода мгновенно применяется ко всем генераторам, а все обнуляемые данные стираются согласно матрице сброса.
3.  **Корректность оффлайн-расчетов**: Симуляция оффлайна на 10 минут, 1 час и 2 часа начисляет ресурсы строго в соответствии с формулой (5.2). Превышение лимита в 2 часа (без улучшений) не должно приводить к начислению дополнительного дохода.
4.  **Стабильность UI**: Числа свыше $1.0e308$ не вызывают сбоев интерфейса, отображаются корректно в выбранном формате (Standard/Scientific) и не выходят за рамки визуальных контейнеров.
